# 2026-08-06 — 알림 정밀도 수정 (KERNEL_VM_PRESSURE 스팸 제거 + 압박 기반 재설계)

## 배경

사용자가 텔레그램 알림을 "스팸처럼 느껴진다"고 보고. 로그로 검증한 결과 사용자 직감이 맞았고,
문제는 그보다 컸다 — **조용해야 할 때 울고, 울어야 할 때 조용했다.**

### 측정된 실패

8일치 로그(2026-07-30 ~ 08-06) 대조:

| 항목 | 값 |
|---|---|
| `KERNEL_VM_PRESSURE` 감지 | 121건 (08-04만 81건, 08-06 33건) |
| 실제 OOM kill | **0건** (dmesg 전수 무흔적) |
| WSL 붕괴 | 0건 |
| → 정밀도 | **0%** |

알림 발사 시점의 시스템 상태는 전부 평온했다:

```
[06:39:07] VHD_IO:40KB/s   MEM:6364M/9947M  HID:27MB  LEVEL:normal
[07:03:23] VHD_IO:14KB/s   MEM:6542M/9947M  HID:24MB  LEVEL:normal
[14:10:03] VHD_IO:30KB/s   MEM:6806M/9947M  HID:0MB   LEVEL:normal
```

반대로 진짜 위험했던 순간엔 **아무 알림도 나가지 않았다**:

```
[15:22:56] VHD_IO:21731KB/s   MEM:9823M/9947M(98.7%)  SWAP:52M    HID:2074MB
[15:23:05] VHD_IO:399282KB/s  MEM:9831M/9947M(98.8%)  SWAP:1997M  HID:3398MB
```

`HIDDEN_BLOAT`는 3주기 연속 요건에 2주기만 걸려 탈락했고, `KERNEL_VM_PRESSURE`는
1분 46초 뒤에야 "누적 39회"라는 무의미한 문구로 도착했다.

### 근본 원인

`monitor.sh:202`의 판정이 `(( vmw > vmw_prev ))` — 누적 카운트가 1이라도 늘면 발사다.
누적값은 단조증가하므로 시간이 지나면 **반드시** 다시 울린다. 임계가 없는 감시다.
10분 쿨다운은 빈도만 늦출 뿐 종착점이 없다.

### 전제가 부정된 가설

원래 설계는 `__vm_enough_memory`를 "OOM 붕괴의 선행 신호"로 가정했다. 데이터가 이를 부정한다:

| 검증 | 결과 |
|---|---|
| 경고 발생 시점의 메모리 (6일, 119건 전수) | **최대 77.2%** — 90% 초과 0건 |
| 08-06 15:23 실제 압박 사건 때 경고 | **0건** (경고는 1분 46초 *뒤*부터) |
| 경고 원문 | `pid: 222, comm: init` — 47회 전부 동일 |

이 경고는 커널이 overcommit 회계로 할당을 **거부한** 기록이다. 프로세스는 죽지 않았고
방어가 작동했다는 뜻에 가깝다. 시스템 메모리 압박과 상관이 없다.

따라서 최초 승인안(`경고 급증 AND 메모리 AND I/O`)은 폐기했다. 3일 시뮬레이션에서
발사 0건 — 15:23 사건조차 못 잡았다. 경고를 AND 조건에 두면 경고가 안 뜬 진짜 위험을
필터로 걸러 버린다.

## Goal

알림 정밀도를 0%에서 실용 수준으로 올린다. 스팸을 제거하되 2026-08-06 15:23 같은
실제 압박 사건은 포착한다.

## 설계

압박 지표 자체를 트리거로 올리고, 커널 경고는 알림 본문의 **참고 정보**로 강등한다
(신호를 버리지 않되 판정에서 뺀다).

```
MEM >= 90%  AND  (VHD_IO >= 100MB/s  OR  HID >= 1500MB)
  -> 2주기 연속 시 발사, 30분 쿨다운
  -> 급등(HID >= 3000MB 또는 MEM >= 95%)이면 1주기 즉시
```

## 범위 밖 (별도 작업 단위로 분리)

조사 중 `docs/progress.md`의 핵심 전제가 틀렸음을 확인했다:

```
Ubuntu ns      pid namespace inode = 4026532223
wsl --system   pid namespace inode = 4026532211   <- 서로 다름, 둘 다 루트 아님
wsl --system 의 pid2 = systemd                     <- 루트 ns라면 kthreadd 여야 함

```

`wsl --system`은 루트 PID 네임스페이스가 **아니다**. 따라서 2026-07-22에 구축한
`ROOTNS_GUARD`의 OOM 면제는 진짜 배관 init(pid 222)에 도달하지 못하고 엉뚱한
프로세스(pid 22, rss 1.8MB)에 `-1000`을 걸고 있다. **작동하지 않는 방어다.**

이번 작업에는 **문서 정정까지만** 포함한다. 실제 대응(진짜 루트 ns 접근이 WSL 구조상
가능한지 조사 → 불가능하면 관측 기반 방어로 전환)은 별도 작업 단위로 다룬다.

### 부수 확인

- `monitor.sh stop` 직후 `pgrep`에 옛 PID가 잡혀 중복 실행을 의심했으나, SIGTERM 처리 중
  잔상이었다. 확인 결과 정상 종료됐고 고아는 없다.
- 재기동 후 프로세스가 2개 보이는 것은 정상이다. 두 번째는 `_notify_after_debounce`로
  60초 뒤 Started 알림을 보내고 스스로 종료한다(자식이 `sleep 60`인 것으로 식별).
- **`pgrep -f 'monitor.sh start'`는 자기 자신을 실행한 셸까지 센다.** 관측 스크립트가
  monitor를 2개로 보고했으나 `ps -eo pid,ppid,cmd`로 확인하니 실제로는 1개였다.
  이 패턴으로 프로세스 수를 세면 항상 +1이 된다.
- **기존 bats 실패 2건은 이번 변경과 무관하다.** `do_status`가 미실행 시 `return 1`을
  반환하는데 테스트가 `output=$(bash "$MONITOR_SCRIPT" status)`로 실행해 non-zero exit에서
  실패 처리된다. `git archive HEAD`로 원본을 풀어 돌린 결과 동일하게 실패했다.
  테스트 쪽 결함이며 이번 범위 밖이라 손대지 않았다.

### 구현 중 추가로 고친 것 (계획에 없던 정리)

셋 다 이번 변경이 만든 불일치를 없애는 것으로, 동작 변경은 없다.

- 알림 본문의 `평시 ~26MB` → `(임계 1500MB)`. 방금 반증한 기준선을 알림에 남기면
  잘못된 척도를 계속 제시하게 된다.
- `최근 60초` → `직전 60초 창`. `vmw_burst`는 직전에 *완료된* 창의 값이라 최대 60초
  지연된다. 판정에 쓰지 않는 참고 정보에 슬라이딩 창까지 구현하는 것은 과하다고 보고
  문구로 사실을 드러냈다.
- 변수명 `hidden_warned`/`hidden_high_streak`/`hidden_last_alert` → `pressure_*`.
  판정 대상이 "숨은 메모리"에서 "압박"으로 바뀌어 이름과 의미가 어긋났다.

### 알려진 한계

- **HID 게이지는 여전히 절반 눈이 멀어 있다.** `n/a` 표기로 그 사실이 드러나게만 했을 뿐,
  이중계상 자체는 해결하지 못했다(`Pss_Anon`은 권한 부족으로 배제). 현재 상시 `n/a`이므로
  압박 판정은 실질적으로 `MEM ≥ 90% AND IO ≥ 100MB/s`로 동작한다. 08-06 15:23 사건은
  I/O가 390MB/s였으므로 이 경로로도 잡힌다.
- **임계 90%의 근거는 6일 표본이다.** 평시 최대가 83.1%였고 사건이 98.8%였다는 관측에
  기반한다. 더 긴 표본에서 평시 90%대가 나타나면 재조정이 필요하다.
- **`ROOTNS_GUARD`는 작동하지 않는 채로 남아 있다.** 위 "범위 밖" 절 참조. 이번 작업은
  문서 정정만 했다.
- 30분 관측 구간에 압박 사건이 없었으므로 **실제 발사 경로는 리플레이로만 검증**됐다.
